LocalLLMChat — Architecture

LocalLLMChat is a native SwiftUI chat app for macOS that runs language models entirely on-device (CoreAIKit models, streaming Markdown replies). A background agent also builds a daily news digest with the same local model and publishes it as a Pages document — on schedule, even when the app is closed.

A personal project to explore what a local-LLM app looks like when designed as a proper macOS citizen: three processes (UI app, launchd agent, XPC worker), a versioned XPC protocol with streaming and at-most-once semantics, a supervised model process, and everything time- or I/O-dependent behind protocols so the logic is testable on fakes.

This page shows the target architecture; each part is marked with its status (October 2026).

1. The big picture

Three processes. The Gateway is the single owner of state; the UI is a view; the Worker only runs the model. Each process trusts only its neighbour, and in the target every connection verifies the peer's code signature.

How to read it:

  • Only the Gateway talks to the Worker. The UI never does, and the Worker never touches the network: model downloads happen in the Gateway, which hands the Worker a local path.
  • Built: the Gateway's scheduler and digest job (inference runs in the worker), WorkerSupervisor, the Worker itself, the settings screen and installer, the UI↔Gateway protocol (handshake, request IDs, pushed events), and a first chat slice: a reply is generated by the worker through GatewayChatService and RemoteChatRuntime.
  • Planned: Gateway-owned conversations and model catalog, chat hardening (recovery after restart), peer authentication, lifecycle handling (updates, sleep, thermal), tool calls across processes, and sandboxing the worker.

3. Wire contracts

Both hops use the same pattern: one XPC method carrying a versioned JSON envelope, so the schema can evolve without touching the Objective-C protocol ("interface only grows").

UI ↔ Gateway Gateway ↔ Worker
File Sources/Gateway/GatewayIPC.swift, GatewayEvents.swift Sources/Shared/WorkerIPC.swift
Channel Mach service com.example.localllmchat.gateway embedded XPC service com.example.localllmchat.worker
Objective-C protocol GatewayXPCProtocol.send(Data, reply:) + client-exported GatewayEventSinkXPC WorkerXPCProtocol.send(Data, reply:) + WorkerEventSinkXPC.deliver(Data, ack:)
Streaming status and chat events pushed to the client, ack-gated batches, strictly increasing sequence worker → gateway event batches, ack-gated, strictly increasing sequence
Correlation requestID on everything; mutating requests run at most once (bounded ledger of 128); requestStatus(id) after reconnect instead of re-sending requestID on every call, reply and event
Connection one long-lived connection, ping every 5 s, reconnect on interruption one long-lived, supervised (XPCWorkerLink)
Version check hello handshake first, then every envelope; mismatch → unsupportedProtocol (protocol 3, no dual stack) hello handshake + every envelope
Peer auth (planned) code-signing requirement (team ID + identifier + min version), audit token rather than PID same

4. Bundle layout and build targets

Target Type Sources Notes
LocalLLMChat application (macOS) Sources/ Gateway code lives under Sources/Gateway/
LocalLLMGateway application, macOS, LSUIElement Gateway/, Sources/Gateway/, Sources/Shared/ Must be an .app: embedded XPC lookup is relative to the caller's main bundle (verified with a spike)
LocalLLMWorker xpc-service, macOS Worker/, Sources/Shared/ ServiceType: Application, no network code
LocalLLMChatTests unit tests, macOS Tests/ hosted in the app; everything runs on fakes

Sources/Shared/ is compiled into both the Gateway and the Worker: it holds the Worker wire types, WorkerEngine, and FileQuarantine. Target signing: hardened runtime without disable-library-validation, per-process entitlements, no codesign --deep.

5. Known limitations and next steps

Limitation today Why it matters Next step
A lost reply (Gateway closed or restarted mid-generation) fails the turn and rolls it back The user loses the reply Recovery by requestID, partial transcript on Stop, explicit not-installed and "queued" states
Conversations and downloads are owned by the UI; each request carries the whole transcript The Gateway cannot serve them when the app is closed Move conversations, request queue and model catalog into the Gateway
No code-signing requirement on either XPC hop Any local process can call the Gateway setCodeSigningRequirement on both hops, hardened runtime, verified with real team signing
Gateway version handling is manual after a rebuild; no sleep / session-resign / thermal handling beyond wake An app update can leave a stale agent running Old agent yields to a newer app; lifecycle events defer or unload work
Tool calls do not cross processes No tool use on the worker path Tool bridge Worker → Gateway → UI
Worker is not sandboxed Model-loading code has user-level file access App sandbox for the XPC service
Push events and reconnect are covered by tests on fakes only A regression in the real XPC path could go unnoticed Live smoke test across a real launchd restart
